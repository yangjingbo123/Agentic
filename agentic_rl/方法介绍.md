# 面向大语言模型测试时推理的分层多智能体强化学习框架

---

## 0. 方法总览（一句话定义）

> 我们提出一个分层多智能体强化学习框架：高层 Controller 负责推理策略调度，低层 Proposer / Critic / Verifier 通过**可学习的自然语言交互动作**协作完成数学推理，所有角色的生成行为均通过终局正确性奖励（GRPO）进行联合优化。

---

## 术语定义

以下术语在全文中含义固定，不混用：

| 术语              | 定义                                                  | 示例                                |
| --------------- | --------------------------------------------------- | --------------------------------- |
| **episode**     | 针对一道题的一次完整推理过程，从 Controller 第一次输出到 majority vote 结束 | 一道 GSM8K 题的完整解答                   |
| **round**       | Controller 发出一次 meta-plan 后，低层三角色完成的一次协作周期          | 一次 explore 或 verify               |
| **turn**        | 某个角色的一次完整 LLM 生成，包含本职内容和可选的 `<interaction>` 意图      | Proposer 生成一段推理链                  |
| **interaction** | 某角色在 turn 内发出的交互意图，以及由此触发的目标角色响应（合称一次 interaction）  | `request_verifier` 及 Verifier 的回应 |
| **rollout**     | 采样一个完整 episode 的过程（推理阶段，无梯度）                        | GRPO 采样 N=4 个 episode             |
| **trace**       | Proposer 写入黑板的一条推理记录，包含推理过程和候选答案                    | `(reasoning, "18")`               |
| **trajectory**  | 一个 episode 内所有 turn 的 token 序列，用于训练                 | 所有角色输出的 token 拼接                  |

**关系说明：**

```
1 episode = 若干round（Controller每轮决策，strategy=stop或达到max_rounds时结束）
1 round   = 1次Controller决策 + 1个起始turn + 若干interaction（≤ max_interactions）
1 turn    = 本职内容 + <interaction>意图（可选）
1 interaction = 发起方意图 + 目标方响应turn（共2个turn）
```

## 1. 我们在解决什么问题

### 1.1 背景：大模型做数学题的现状

当我们让大语言模型（LLM）解一道数学题时，最常见的做法是：给它一个提示词，让它一步步推理，最后给出答案。这种方式叫做**链式思维（Chain-of-Thought）**。

这种方式有一个根本问题：**整个推理过程是一次性的、固定的**。模型写完就完了，没有人检查它有没有算错，没有人质疑它的逻辑，也没有人验证答案是否正确。

### 1.2 已有的改进思路：多智能体

为了解决这个问题，研究者开始尝试用**多个智能体**来协作推理：

- 一个智能体负责提出解法
- 另一个智能体负责挑错
- 再一个智能体负责验证

这样就形成了一个"提出→批评→验证"的流程，比单个模型独自推理要可靠得多。

### 1.3 现有多智能体方法的局限

但是，现有的多智能体方法大多是**脚本化的**：先让A说话，再让B说话，再让C说话，顺序固定，谁也不能主动找谁说话。

这就好比三个人开会，但规定必须按照"甲→乙→丙→甲→乙→丙"的顺序发言，甲不能打断乙，乙不能向丙提问。这显然不是真正的协作。

更重要的是，**这些智能体的行为本身从来没有被训练过**。它们只是按照人工设计的流程执行，而不是通过经验学习"什么时候该质疑、什么时候该请求帮助"。

### 1.4 我们的核心主张

> **智能体之间的交互行为本身，应该是可以被强化学习优化的。**

具体来说，我们希望每个低层智能体不只是做自己的本职工作，还能学会：

- **什么时候应该请求另一个智能体帮忙**（比如Proposer发现自己不确定，主动请Verifier来验证）
- **什么时候应该质疑另一个智能体的判断**（比如Critic认为Verifier给的分数太高，提出质疑）
- **什么时候应该支持某个已有的答案**（比如Verifier验证后认为某个答案是对的，明确表态支持）

这些"请求、质疑、支持"的行为，我们把它们叫做**交互动作**，它们由LLM用自然语言生成，并通过强化学习来优化。

## 2. 我们的方法：整体思路

### 2.1 两层结构

我们把整个推理过程分成**两个层次**，对应两种不同粒度的决策：

**高层（Controller）——"这一轮干什么"**

Controller是一个总指挥。它不直接解题，而是在每一轮开始前，看一眼当前的推理进展，然后决定：

- 现在应该继续探索新解法，还是重点批评已有解法，还是验证某个答案？
- 这一轮应该投入多少计算资源（轻量/标准/重量）？
- 应该重点调度哪个角色来主导这一轮？

**低层（三个角色）——"这一轮里怎么协作"**

低层有三个功能分化的智能体：

| 角色                | 职责            | 对应的证据类型 |
| ----------------- | ------------- | ------- |
| **Proposer（提出者）** | 生成推理链和候选答案    | 正向证据    |
| **Critic（批评者）**   | 找逻辑漏洞和计算错误    | 负向证据    |
| **Verifier（验证者）** | 独立验证答案，给出置信分数 | 诊断证据    |

这三个角色不是按固定顺序执行的。每个角色在完成本职工作后，还会生成一条**交互意图**，说明自己想不想找别人说话、找谁、说什么。

### 2.2 Controller 的精确职责

Controller **每个 round 开头执行一次**，读取最新黑板状态后输出 meta-plan，动态决定本轮策略：

| 字段 | 含义 | 取值 |
|------|------|------|
| `strategy` | 本轮推理策略 | explore / refine / verify / stop |
| `focus` | 本轮**起始角色**（不是唯一角色） | proposer / critic / verifier / balanced |
| `reason` | 一句话说明理由 | 自然语言 |

**几点明确说明：**
- Controller 每轮都能看到最新黑板，可以根据当前证据动态调整策略（这是与固定流程的核心区别）
- `focus` 决定起始角色，不是本轮唯一角色。起始角色执行后，若发出交互意图，其他角色仍可被触发
- 若 `strategy=stop`，跳过本轮低层协作，直接进入 majority vote
- 全局上限 `max_rounds=3`，防止无限循环；Controller 可在达到上限前主动 stop

这与 ReMA 的设计一致：高层 meta-thinking 与低层 reasoning **交替执行**，高层每轮都能感知低层的最新进展。

### 2.3 一个具体的例子

假设题目是："小明有15个苹果，给了小红三分之一，又买了8个，现在有多少个？"

**Round 1 开头：Controller 分析**
> 黑板为空，应该先探索。strategy=explore，focus=proposer。

**Proposer 工作**
> 推理：15×(1/3)=5，给出5个，剩10个，再买8个，共18个。答案：18。
> 交互意图：不太确定，request_verifier。

**Verifier 响应**
> 独立计算：15-5+8=18。分数：0.95。support:18。

**Round 2 开头：Controller 分析**
> 黑板：已有答案18，置信0.95，Verifier支持。strategy=stop。

**结束**
> Majority vote：18。reward=1。

### 3.2 交互动作的格式

每个低层角色在输出本职内容的同时，还会生成一段 `<interaction>` 标签：

```
<interaction>
action: request_critic          ← 动作类型
target: critic                  ← 目标角色
reason: 我对第3步的计算不确定   ← 理由
</interaction>
```

**完整动作空间：**

| 动作                 | 是否触发响应 | 触发谁      | 作用                            | 写入黑板           |
| ------------------ | ------ | -------- | ----------------------------- | -------------- |
| `none`             | 否      | —        | 不交互，继续                        | 否              |
| `request_critic`   | 是      | Critic   | 请求审查当前解法                      | 记录 interaction |
| `request_verifier` | 是      | Verifier | 请求验证当前答案                      | 记录 interaction |
| `request_proposer` | 是      | Proposer | 请求重新提出解法                      | 记录 interaction |
| `support:<答案>`     | 否      | —        | 明确表态支持某答案，影响 majority vote 权重 | 记录 interaction |
| `challenge:<问题描述>` | 是      | target   | 质疑目标角色的判断，目标角色需重新回应           | 记录 interaction |

**关于 `support` 的作用**：不只是日志记录。`support:<答案>` 会增加该答案在黑板 scores 中的权重，影响最终 majority vote 的结果。

**关于 `challenge` 的响应方式**：目标角色收到 challenge 后，会看到发起方的完整输出和质疑内容，生成一个**修正或补充解释**的新 turn，而不是从头重新回答。

**解析失败处理**：若 `<interaction>` 标签缺失或格式错误，视为 `action=none`，不触发任何响应。不允许一个 turn 内出现多个 `<interaction>` 标签，只取第一个。

### 3.3 交互状态机

每个 round 内的交互执行流程如下：

```
输入：起始角色 R，问题 Q，meta-plan，黑板状态

1. R 执行本职 turn，输出内容写入黑板
2. 解析 R 的 <interaction> 意图
3. 若 action == none 或 action == support：
       记录到黑板，结束本 round 的交互
4. 若 action 触发响应（request_* 或 challenge）：
       interaction_count += 1
       若 interaction_count > max_interactions：强制停止
       目标角色 T 生成响应 turn，写入黑板
       以 T 的输出为新的发起方，回到步骤 2
5. 若本 round 没有 Proposer 输出：
       补充执行一次 Proposer turn
```

`max_interactions=3` 是**每个 round** 内的上限，不是整个 episode 的上限。一个 episode 最多触发 `budget × max_interactions` 次交互。

### 3.4 Blackboard 数据结构与可见性

```python
Blackboard = {
    "traces":       [(reasoning: str, answer: str), ...],  # Proposer写入
    "flaws":        [{"content": str}, ...],               # Critic写入
    "scores":       [(answer: str, score: float), ...],    # Verifier写入
    "interactions": [{"from": str, "action": str,
                      "target": str, "reason": str}, ...], # 所有角色写入
}
```

**可见性规则：**

- 黑板对所有角色**全文可见**，没有信息隔离
- Controller 通过 `to_text()` 读取压缩摘要（约100字），不读取原始黑板
- 低层角色在 user prompt 中直接接收 `to_text()` 摘要

**`to_text()` 摘要内容：**

- 已有解法数量和候选答案列表
- 最近一条 flaw 的前80字
- 置信分数最高的答案及其分数
- 最近一次 interaction 的摘要

旧信息不会被截断，但 `to_text()` 只取各字段的最新/最优条目，不会随轮数增长而无限膨胀。

## 4. 训练方法详解

### 4.0 本框架与强化学习的对应关系

本框架的训练过程本质上是**强化学习（Policy Gradient）**，GRPO 是其具体实现。

| RL 概念 | 本框架对应 |
|---------|-----------|
| 环境（Environment） | 数学题 + `run_episode()` 执行交互、返回 reward |
| 状态（State） | 黑板状态 + 问题文本 |
| 动作（Action） | 各角色生成的 token 序列（含 `<interaction>` 标签） |
| 奖励（Reward） | 答案正确性（稀疏）+ Critic 中间奖励 |
| 策略（Policy） | 各角色的 LoRA 参数 |
| Episode | 一道题的完整推理过程 |
| Value Network | **无**，GRPO 用组内对比替代 |

**一道题的完整训练流程：**

1. **采样**：同一道题跑 N=4 个独立 episode（无梯度），收集每个 turn 的 log_probs 和最终 reward
2. **Advantage**：组内归一化 `A_i = (r_i - mean_r) / std_r`，答对的 episode advantage > 0，答错的 < 0
3. **Loss**：对每个 turn 重新 forward，用 advantage 加权的 clipped policy loss 更新 LoRA
4. **更新**：四个角色各自独立 backward + optimizer.step()

核心直觉：同一道题，4 个 episode 形成对比——答对的 episode 里所有行为（推理方式、交互动作、验证决策）都被强化，答错的被抑制。**不需要人工标注"哪步推理是对的"，只需要知道最终答案对不对。**

---

### 4.0 智能体如何学会交互

这是理解本框架的关键问题：**智能体并不是预先被告知"什么时候该交互"的，而是通过 RL 从结果中学到的。**

训练分两层：

**第一层：格式约束（prompt 定义动作空间）**

每个角色的 system prompt 规定了输出格式，包含 `<interaction>` 标签和可选的动作类型（`none / request_* / support / challenge`）。这只是告诉模型"你有这些选项"，不规定何时使用。

**第二层：奖励信号（RL 训练动作策略）**

训练时，每个 episode 结束后根据最终答案是否正确分配奖励，并通过 GRPO 反向传播到每一个 turn 的 LoRA 参数，包括 `<interaction>` 标签内的 token。

结果：
- 若某次 Proposer 发出 `request_critic` 后最终答案正确 → 这个"主动请求"行为被强化
- 若某次 Critic 发出 flaw 但答案本来是对的 → 这个"误报"行为被惩罚（-0.1）
- 若某次 Verifier 给出高分支持了正确答案 → 这个"支持"行为被强化

**`<interaction>` 标签的 token 与正文 token 使用完全相同的 loss weight**，没有特殊处理。交互行为是从终局正确性奖励中自然涌现的，不是人工规则写死的。

---

### 4.1 训练目标与算法定位

我们的优化目标是**最终答案正确率**，奖励信号为：

$$r \in \{0, 1\}, \quad r = \mathbf{1}[\text{majority\_vote}(\text{traces}) = \text{correct\_answer}]$$

我们采用的算法统一称为：**Group-Relative Reward Estimation + Turn-level Clipped Policy Optimization**，简称 **GRPO-Turn**。

它不是标准PPO，也不是纯GRPO，而是两者的结合：

- **GRPO部分**：组内相对奖励计算 advantage，无需 Value 网络
- **Turn-level部分**：以 turn 为粒度计算概率比和 clip，而非 token 级别

### 4.2 GRPO：组内相对 Advantage

对同一道题采样 $N=4$ 个完整 episode（rollout），计算组内归一化 advantage：

$$A_i = \frac{r_i - \bar{r}}{\sigma_r + \epsilon}$$

其中 $r_i \in \{0,1\}$ 是第 $i$ 个 episode 的终局奖励，$\bar{r}$ 是组内均值。

**这个 advantage 是 episode 级别的标量**，代表"这个 episode 整体比平均水平好多少"。它会被广播到该 episode 内所有有效 turn 上参与 loss 计算。

**为什么不需要 Value 网络**：标准 PPO 需要 Value 网络估计每一步的期望回报，显存开销大。GRPO 用组内对比替代了这个估计，4个 episode 的相对表现就是天然的 baseline。

### 4.3 Turn-level Clipped Policy Optimization

**为什么不用 token-level**：一个 episode 包含多个 turn（Controller + 若干 Proposer/Critic/Verifier + 交互响应），每个 turn 数百 token。Token 级别的概率比方差极大，梯度信号不稳定。

我们以 turn 为粒度计算概率比，turn 内所有 token 的 log 概率差取均值后再取指数：

$$\rho_t = \exp\!\left(\frac{1}{|t|}\sum_{k \in t}\bigl[\log\pi_\theta(a_k) - \log\pi_{\text{old}}(a_k)\bigr]\right)$$

每个 turn 的有效 advantage 为：

$$A_t^{\text{eff}} = A_i \cdot r_t - \lambda_{\text{KL}} \cdot \text{KL}_t$$

其中 $r_t$ 是该 turn 的奖励（见4.4节），$\text{KL}_t$ 是该 turn 相对 reference model 的 KL 散度。

**Dual-clip PPO loss**（来自 ReMA）：

$$\mathcal{L}_t = \begin{cases}
-\min\!\left(\rho_t A_t^{\text{eff}},\ \operatorname{clip}(\rho_t, 1\pm\varepsilon) \cdot A_t^{\text{eff}}\right) & A_t^{\text{eff}} \geq 0 \\
\min\!\left(\text{上式},\ -c \cdot A_t^{\text{eff}}\right) & A_t^{\text{eff}} < 0
\end{cases}$$

其中 $\varepsilon=0.02$（比标准 PPO 的 0.1-0.2 更小，因为 turn-level ratio 方差更大），$c=3$（dual-clip 系数，防止对负 advantage 过度惩罚）。

### 4.4 奖励设计：终局奖励 + 角色级中间奖励

为缓解多轮多角色协作中的 credit assignment 问题，我们在终局正确性奖励之外引入轻量的角色级中间奖励。完整 turn-level reward 定义为：

$$r_t = r_t^{\text{terminal}} + \mathbf{1}[\text{role}(t)=\text{Proposer}]\, r_t^{\text{prop}} + \mathbf{1}[\text{role}(t)=\text{Critic}]\, r_t^{\text{crit}}$$

**终局奖励**（主信号，只分配给 episode 最后一个 turn）：

$$r_t^{\text{terminal}} = \begin{cases} 1.0, & t=T \ \text{且}\ \text{majority\_vote}(\mathcal{B}) = a^* \\ 0, & \text{otherwise} \end{cases}$$

**Proposer 中间奖励**（鼓励每个 round 生成正确候选答案，episode 内总和 cap at 0.3）：

$$r_t^{\text{prop}} = 0.3 \cdot \frac{\mathbb{1}[a_t = a^*]}{N_p}$$

其中 $a_t$ 是该 Proposer turn 的候选答案，$a^*$ 是标准答案，$N_p$ 是该 episode 内 Proposer turn 的数量。归一化保证辅助奖励总量不超过 0.3，终局奖励始终是主信号。

**Critic 挑错时机校准奖励**（评价 Critic 是否在正确时机触发错误反馈，不评价 flaw 的语义质量）：

$$r_t^{\text{crit}} = \begin{cases} +0.2, & \text{Critic 发出 flaw 且当前候选答案错误} \\ -0.1, & \text{Critic 发出 flaw 且当前候选答案正确} \\ 0, & \text{Critic 未发出 flaw} \end{cases}$$

该设计防止 Critic 学会"无脑挑错"——只有在答案确实有误时挑错才有正奖励。

**episode 级总奖励**为所有 turn-level reward 之和，用于 GRPO advantage 计算：

$$R_i = \sum_{t \in \tau_i} r_t, \qquad A_i = \frac{R_i - \bar{R}}{\sigma_R + \epsilon}$$

**与 MMOA-RAG 的关系**：MMOA-RAG 以最终答案 F1 为 shared reward，并为不同模块加入格式、长度、数量相关的 penalty；我们的中间奖励直接绑定数学推理过程中的候选答案正确性与 Critic 挑错校准，不依赖额外的检索相关性标注或过程奖励模型。

### 4.5 Majority Vote 的对象

**Majority vote 在单个 episode 内部进行**，对象是该 episode 内所有 Proposer 写入黑板的候选答案（traces）：

```python
# 一个 episode 内可能有多个 trace（每个 round 至少一个 Proposer 输出）
answers = [ans for _, ans in blackboard.traces]
final_answer = Counter(answers).most_common(1)[0][0]
```

Verifier 输出的是置信分数，不直接参与投票，但其分数影响 `support` 动作的权重。

**与 self-consistency 的区别**：self-consistency 是对同一题目采样多个独立 trajectory 后投票；我们的 majority vote 是在单个 trajectory 内部、多个 round 产生的候选答案之间投票。GRPO 的 N=4 采样是为了计算 advantage，不是为了 majority vote。

### 4.6 各角色的训练粒度

| 角色         | 参与梯度计算的内容                                    | 获得奖励的条件              |
| ---------- | -------------------------------------------- | -------------------- |
| Controller | meta-plan 的所有 token（含 strategy/budget/focus） | 同 episode 末 turn 的奖励 |
| Proposer   | 推理链 + 答案 + `<interaction>` 标签的所有 token       | 同上                   |
| Critic     | 错误分析 + `<interaction>` 标签的所有 token           | 同上                   |
| Verifier   | 验证说明 + 分数 + `<interaction>` 标签的所有 token      | 若是末 turn 则直接获得奖励     |

`<interaction>` 标签内的 token 与正文 token 使用**相同的 policy head 和相同的 loss weight**，没有特殊处理。各角色使用独立的 optimizer，loss 不加权（权重均为1）。

### 4.7 KL 约束与训练稳定性

为防止训练 collapse（ReMA README 明确警告了这一点），我们加入两个稳定机制：

**Reference model**：每个角色保留一个冻结的初始模型副本，训练时计算当前策略与初始策略的 KL 散度，加入 reward 惩罚：

$$r_t^{\text{eff}} = r_t - \lambda_{\text{KL}} \cdot \text{KL}(\pi_\theta \| \pi_{\text{ref}})_t$$

**AdaptiveKLController**：自动调整 $\lambda_{\text{KL}}$。若当前 KL 超过目标值，增大系数（更强约束）；低于目标值，减小系数（放松约束）。无需手动调参。

**梯度裁剪**：每个角色的梯度 norm 裁剪到 1.0，防止多轮对话的梯度爆炸。

## 5. 工程实现

### 5.1 硬件配置与显存分配

我们使用三张 NVIDIA A6000（每张 48GB，共 144GB），四个角色各自加载独立的 Qwen3-8B 实例（bfloat16，约 16GB/个）：

| GPU | 角色 | 推理显存 | 训练显存（LoRA） |
|-----|------|----------|----------------|
| GPU 0 | Controller | ~16GB | ~16GB + <1GB |
| GPU 1 | Proposer | ~16GB | ~16GB + <1GB |
| GPU 2 | Critic + Verifier | ~32GB | ~32GB + <1GB |

训练时 base model 全程冻结，只有 LoRA 参数产生梯度和 optimizer state（每套 LoRA 约 26MB，4套合计 <1GB），总显存占用约 65GB，三张卡完全够用。

**与 ReMA/MMOA-RAG 的对比**：两者均采用全量参数训练（FSDP 分布式），每个模型训练显存约 56GB（参数 + 梯度 + optimizer state），需要更多卡支撑。我们在三张 A6000 的硬件约束下选择 LoRA，是合理的工程权衡。

**后续扩展**：若实验结果显示 LoRA 表达能力不足，可升级为 rank=64/128 的大 LoRA（更新参数量约 0.5-1%，效果接近全量训练），或在获得更多卡后切换为全量 FSDP 训练。两种方案的代码改动均局限在 `trainable_llm.py`，不影响其他模块。

### 5.2 LoRA 微调配置

每个角色模型独立挂载一套 LoRA，四个角色各自有独立的 optimizer，梯度互不干扰：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| LoRA rank | 16 | 初始实验；不足时升级至 64/128 |
| 目标模块 | q_proj, v_proj | 注意力层 |
| 可训练参数比例 | ~0.1% | base model 全程冻结 |
| optimizer | AdamW（独立×4） | 各角色梯度互不干扰 |

与 ReMA 的 Separate Parameters 模式一致：Controller 和低层三角色参数完全分离，可以独立优化。

## 6. 实验设计

### 6.1 数据集与 Benchmark

我们采用三个难度递进的 benchmark，覆盖从验证框架可行性到挑战性评测的完整范围：

| Benchmark           | 难度     | 规模              | 用途              |
| ------------------- | ------ | --------------- | --------------- |
| **GSM8K**           | 小学数学   | 训练7473 / 测试1319 | 冒烟测试，验证框架能跑通    |
| **MATH（Level 3-5）** | 竞赛数学   | 训练7500 / 测试5000 | 主实验，核心指标        |
| **AIME 2024/2025**  | 美国数学竞赛 | 各30题            | 挑战性评测，与ReMA直接对比 |

**选择理由：**

- GSM8K 当前 SOTA 接近 100%，仅用于验证框架基本可行性，不作为主要发表指标
- MATH Level 3-5 是当前多智能体推理论文的主流 benchmark，当前最强模型约 85-90%，仍有提升空间，reviewer 认可度高
- AIME 答案为 0-999 的整数，便于自动评测；ReMA 论文本身使用 AIME 作为主要 benchmark，采用相同设置便于直接对比

### 6.2 对比实验

我们设计了四组对比，逐步验证每个设计的贡献：

| 方法                 | 说明                         | 验证什么          |
| ------------------ | -------------------------- | ------------- |
| **Baseline**       | 固定流程P→C→V，LLM不训练           | 不训练的上限        |
| **无交互 Agentic RL** | 去掉`<interaction>`，只用GRPO训练 | 训练本身的贡献       |
| **无Controller**    | 去掉高层，低层固定轮数                | Controller的贡献 |
| **完整框架（本方法）**      | 分层MARL + 交互可学习 + GRPO      | 完整方法          |

### 6.3 评估指标

- **Accuracy**：答案正确率（主指标）
- **Avg Turns**：平均推理轮数（衡量效率）
- **Interaction Rate**：每个episode平均触发的交互次数（衡量协作行为是否被学到）

### 6.4 公平性说明

为保证对比实验的公平性，所有方法在以下条件下统一：

| 控制变量                  | 设定                                                     |
| --------------------- | ------------------------------------------------------ |
| 基础模型 | 相同的 Qwen3-8B checkpoint |
| 最大 token 数            | 每个 turn 上限 512 tokens                                  |
| 推理预算                  | 所有方法的总 token 消耗上限相同（通过 budget 控制）                      |
| 采样温度                  | 训练时 temperature=1.0，评估时 greedy decoding                |
| Majority vote         | 评估时所有方法均使用单次 greedy decoding，不做多采样投票                   |
| Baseline token budget | Baseline 的固定 P→C→V 流程与本方法 budget=standard 的 token 消耗对齐 |

## 7. 与相关工作的关系

### 7.1 ReMA（2025）

ReMA 将推理过程拆分为高层 meta-thinking（决定推理策略）和低层 reasoning（执行推理），用分层MARL训练。

**本方法的继承**：分层结构的设计思路来自ReMA。

**本方法的区别**：ReMA的低层执行是固定流程，智能体之间没有显式的交互动作。我们在低层增加了可学习的交互机制。

### 7.2 MAPoRL（2025）

MAPoRL 明确将"多模型协作行为"作为RL的训练对象，而不是假设模型天然会合作。

**本方法的继承**：将协作行为作为训练对象这一核心思想。

**本方法的区别**：MAPoRL的协作行为是在模型输出层面隐式体现的，而我们通过`<interaction>`标签将交互意图**显式化**，使其可解释、可分析。

### 7.3 MMOA-RAG（2024）

MMOA-RAG 将RAG的各个模块（检索、重排、生成）建模为合作agent，用联合优化替代各模块独立优化。

**本方法的继承**：将原本独立的模块建模为协作agent的思路。

**本方法的区别**：我们的场景是推理链生成，而非RAG；我们的交互是动态的（由LLM决定是否触发），而非固定的模块间调用。

### 7.4 本方法的核心创新点总结

> 低层智能体之间的交互意图（请求、质疑、支持）以**自然语言形式**由LLM生成，并通过**GRPO直接优化**，使协作行为本身成为训练对象。这使得系统不再是一个脚本化pipeline，而是一个真正会协商、会分工、会修正的协作体。

## 8. 失败模式分析

主动列出本框架可能出现的失败模式及缓解措施：

| 失败模式                 | 原因                                                       | 缓解措施                                                        |
| -------------------- | -------------------------------------------------------- | ----------------------------------------------------------- |
| **交互爆炸**             | 角色之间反复 challenge，触发次数达到上限                                | `max_interactions=3` 强制截断；超限后直接进入下一 round                   |
| **Proposer 逃避责任**    | Proposer 学会总是输出 `request_verifier` 而不认真推理，把责任推给 Verifier | KL 约束防止策略偏移过快；Verifier 的验证结果仍影响最终奖励                         |
| **Verifier 过度保守**    | Verifier 总是给低分，导致正确答案也被否定                                | 多个 round 的 majority vote 降低单次 Verifier 的影响；训练信号会惩罚导致答错的保守行为 |
| **Controller 偏好短推理** | Controller 学会总是输出 `budget=light` 来减少 token 消耗            | 奖励只看正确率，不惩罚 token 数；若短推理答错，Controller 会被惩罚                  |
| **训练不稳定/collapse**   | 稀疏奖励 + 多轮对话梯度累积                                          | AdaptiveKLController + 梯度裁剪（norm=1.0）+ reference model      |
| **角色漂移**             | 某个角色的输出格式偏离 system prompt 要求                             | 解析失败时 fallback 到默认行为（`action=none`，`score=0.5`）；不会导致训练崩溃    |
