# Agentic RL 框架技术文档

## 1. 概述

本框架是一个面向数学推理任务的**多智能体强化学习（MARL）训练系统**，核心思想是：用一个共享的大语言模型（LLM）同时扮演四个不同角色的智能体，通过角色间的协作与交互来解决数学问题，并用 GRPO 算法对整个多智能体轨迹进行端到端强化学习训练。

**基础模型**：Qwen3-8B  
**训练算法**：GRPO（Group Relative Policy Optimization）+ Dual-Clip PPO  
**推理加速**：vLLM + LoRA 热更新  
**参数效率**：单份 base 模型 + 4 套独立 LoRA adapter，显存只占一份 base（~16GB）

## 3. 模块详解

### 3.1 模型层：`llm/trainable_llm.py`

**核心设计**：单 base 模型 + 多 LoRA adapter 共享显存。

```
base model (Qwen3-8B, bfloat16, ~16GB)
    ├── LoRA adapter: controller  (r=16, alpha=32, q_proj+v_proj)
    ├── LoRA adapter: proposer
    ├── LoRA adapter: critic
    └── LoRA adapter: verifier
```

`SharedModel` 类封装了 PEFT 模型，通过 `set_role(role)` 调用 `peft_model.set_adapter(role)` 切换当前激活的 adapter。每个角色有独立的 LoRA 参数，但共享所有 base 权重，训练时各角色的 optimizer 只更新自己 adapter 的参数。

同时维护一份冻结的 `ref_base`（deepcopy，无梯度），用于 KL 散度计算。

**关键参数**：
- LoRA rank: 16，alpha: 32
- 目标模块：`q_proj`, `v_proj`
- 启用 gradient checkpointing 节省显存

### 3.2 推理引擎：`llm/vllm_engine.py`

训练时用 vLLM 加速推理（占用约 45% GPU 显存），训练模型占用另一部分。

**LoRA 热更新机制**：每个 train_step 结束后，调用 `sync_all_loras()` 将 HF PEFT 的 LoRA 权重保存到临时目录，vLLM 下次生成时通过 `LoRARequest` 加载最新权重，实现训练-推理权重同步。

### 3.3 黑板环境：`envs/blackboard.py`

黑板（Blackboard）是多智能体共享的通信空间，存储四类消息：

| 消息类型 | 写入者 | 内容 |
|---------|--------|------|
| `TRACE` | Proposer | `(reasoning, answer)` 推理链和答案 |
| `FLAW` | Critic | 发现的错误描述 |
| `SCORE` | Verifier | `(answer, score)` 答案置信分 |
| `INTERACTION` | 任意角色 | `{from, action, target, reason}` 交互记录 |

`to_text()` 将黑板状态序列化为自然语言，作为每个智能体的上下文输入。

### 3.4 智能体执行器：`agents/agentic_executor.py`

**Episode 执行流程**（`run_episode`）：

```
for round in range(max_rounds):
    1. Controller 读取黑板 → 输出 strategy + focus
       strategy: explore | refine | verify | stop
       focus: proposer | critic | verifier | balanced

    2. 若 strategy == "stop" → 退出循环

    3. 启动角色（由 focus 决定起始角色）
       → 写入黑板

    4. 交互路由（最多 max_interactions 次）：
       解析输出中的 <interaction> 标签
       → 若 action != none，触发目标角色响应
       → 目标角色写入黑板，可继续触发新交互

    5. 确保 Proposer 至少执行一次

最终：majority_vote(blackboard.traces) → final_answer
```

**交互协议**：每个角色的输出中包含结构化的 `<interaction>` 块：
```xml
<interaction>
action: request_critic | request_verifier | support:<答案> | challenge:<问题> | none
target: critic | verifier | proposer | none
reason: 一句话说明
</interaction>
```

**奖励设计**（多层次）：

| 奖励类型 | 触发条件 | 值 | 分配对象 |
|---------|---------|-----|---------|
| 终局奖励 | 最终答案正确 | +1.0 | 最后一个 turn |
| Proposer 校准奖励 | 该 round 的 Proposer 答案正确 | +0.3/n_rounds | 该 round 的 Proposer turn |
| Critic 时机奖励 | Critic 挑错 且 Proposer 确实错了 | +0.2 | 该 round 的 Critic turn |
| Critic 惩罚 | Critic 挑错 但 Proposer 其实对了 | -0.1 | 该 round 的 Critic turn |

### 3.5 训练器：`training/grpo_trainer.py`

**GRPO 训练流程**（`train_step`）：

```
1. 采样 n_samples=4 个 episode（同一问题，不同随机轨迹）

2. 计算 group-relative advantage：
   advantage_i = (reward_i - mean(rewards)) / std(rewards)

3. 对每个 episode 计算 per-role loss（_compute_per_role_loss）：
   - 重新计算各角色的 log_prob（训练模型 + 参考模型）
   - KL 惩罚：turn_reward = reward - kl_coef * KL(π || π_ref)
   - Turn-level ratio：ratio = exp(mean(new_lp - old_lp))
   - Dual-Clip PPO loss（参考 ReMA）：
       pg_loss = max(-adv*ratio, -adv*clip(ratio, 1-ε, 1+ε))
       若 adv < 0：额外 clip at -adv * 3.0（防止过度惩罚）

4. 各角色独立 backward + AdamW 更新（lr=1e-5）

5. 梯度裁剪（max_norm=1.0）

6. 同步 LoRA 权重到 vLLM

7. 自适应 KL 控制（AdaptiveKLController）：
   按比例误差调整 kl_coef，目标 KL=6.0
```

**自适应 KL 控制**（来自 InstructGPT/ReMA）：
```
proportional_error = clip(current_kl / target_kl - 1, -0.2, 0.2)
kl_coef *= 1 + proportional_error * n_steps / horizon
```

### 3.6 Prompt 设计：`llm/prompt_templates.py`

四个角色各有独立的 system prompt，定义职责和输出格式：

- **Controller**：分析黑板状态，输出 `<meta-plan>` 块（strategy + focus + reason）
- **Proposer**：生成推理链和答案，输出 `<interaction>` + `推理过程：` + `最终答案：`
- **Critic**：审查错误，输出 `<interaction>` + `错误分析：`
- **Verifier**：验证答案，输出 `<interaction>` + `分数: [0-1]` + `验证说明：`

## 4. 数据流

```
数学问题 (question, answer)
    │
    ▼
AgenticExecutor.run_episode()
    │
    ├─ 生成多轮对话轨迹
    │   messages: [{role_name, system, user, response}, ...]
    │   turn_ids: [0,0,0,1,1,2,2,...]  (每个 token 对应的 turn)
    │   log_probs: [lp_0, lp_1, ...]   (每个 token 的 log prob)
    │   rewards: [r_0, r_1, ...]       (每个 turn 的奖励)
    │
    ▼
GRPOAgenticTrainer._compute_per_role_loss()
    │
    ├─ 按 role 分组 messages
    ├─ 重新 forward 计算 new_log_probs（训练模型）
    ├─ 重新 forward 计算 ref_log_probs（参考模型，no_grad）
    ├─ 计算 KL、ratio、Dual-Clip PPO loss
    │
    ▼
各角色 optimizer.step()
    │
    ▼
vllm_engine.sync_all_loras()  (权重同步)
```

## 6. 训练配置

`configs/default.yaml` 关键参数：

```yaml
llm:
  model_path: "/home/nvidia/jingbo/models/Qwen3-8B"

agentic:
  epochs: 3
  batch_size: 16        # 每 epoch 随机采样的题目数
  n_samples: 4          # GRPO group size（同一题采样次数）
  lr: 1.0e-5
  clip_epsilon: 0.02    # PPO clip 范围
  max_tokens: 256       # 每个 turn 最大生成 token 数
  max_rounds: 1         # 每个 episode 最大协作轮数
  max_interactions: 1   # 每轮最大角色间交互次数
  kl_coef: 0.1          # 初始 KL 系数
  target_kl: 6.0        # 自适应 KL 目标值
  max_grad_norm: 1.0
```

## 7. 评估指标

`evaluate.py` 计算三个指标：

| 指标 | 含义 |
|------|------|
| `accuracy` | 最终答案正确率（majority vote） |
| `avg_turns` | 平均每题使用的 turn 数（衡量推理效率） |
| `interaction_rate` | 平均每题触发的角色间交互次数（衡量协作程度） |

答案比较使用 `normalize_answer()`，去除非数字字符后做字符串匹配。

## 9. 关键设计决策

**为什么用单模型多 LoRA 而非多个独立模型？**  
四个独立的 8B 模型需要 ~64GB 显存，单模型多 LoRA 只需 ~16GB base + 少量 LoRA 参数，使单卡训练成为可能。

**为什么用 Turn-level ratio 而非 Token-level？**  
参考 ReMA 的做法，对一个 turn 内所有 token 的 log ratio 取均值再做 exp，减少高方差 token 对梯度的干扰，训练更稳定。

**为什么用 Dual-Clip PPO？**  
当 advantage 为负时，标准 PPO clip 可能对策略施加过大惩罚，导致模型过于保守。Dual-clip 在 `adv < 0` 时额外限制 loss 上界为 `-adv * 3.0`（c=3），防止 collapse。

**黑板的作用？**  
黑板作为多智能体的共享记忆，避免每个角色需要读取完整对话历史，同时提供结构化的状态摘要（`to_text()`），降低 context 长度和信息噪声。

**Majority Vote 的作用？**  
多轮协作中 Proposer 可能提出多个不同答案，majority vote 从 `blackboard.traces` 中选出出现最多的答案作为最终输出，提升鲁棒性。
